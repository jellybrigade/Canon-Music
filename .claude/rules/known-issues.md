# Known Issues & Platform Gotchas

Bugs + non-obvious platform behavior. Terse by design — full forensics live in git history/commit messages if needed.

## WebKitGTK: left-click popup self-closes
`ContextMenu.tsx` outside-click listener could catch the tail of the same click that opened it (Linux/WebKitGTK only; right-click menus unaffected). Fix: outside-close listener deferred via `setTimeout(...,0)`, uses `mousedown` capture + containment check, not `click`. If a new left-click popover "does nothing": check render fires but `document.querySelector` finds nothing — same bug class, don't assume fresh.

## WebKitGTK freeze/thaw compositor crash (Linux)
Focus-loss/regain (WM switch, devtools toggle) can crash the WebProcess (`gdk_window_thaw_toplevel_updates` assertion) and take the whole app down (`wry` doesn't survive WebProcess death). Upstream WebKitGTK/GTK3 bug, not Canon's.
**Current mitigations (all active, don't strip without replacing):**
- `web-process-terminated` signal → `.reload()` instead of crash (`lib.rs` `.setup()`).
- `useAppActivityTracking` stamps `data-app-blurred` on blur; CSS pauses animations while set.
- `webkit2gtk-nvidia-quirk` crate applies NVIDIA-only compositor env fixes; `CANON_WEBKIT_GPU_ACCEL=1` skips it. Replaced a blanket `WEBKIT_DISABLE_COMPOSITING_MODE=1` that made all Linux scrolling sluggish app-wide.
- `"visible": false` in `tauri.conf.json` + `window.show()` on `on_page_load` (5s fallback thread in `.setup()`) — avoids mapping an unpainted webview at creation.
**Do not**: call `set_hardware_acceleration_policy` (`OnDemand`/`Never`) without first checking nothing else touches compositing — `OnDemand` + the old `WEBKIT_DISABLE_COMPOSITING_MODE` env var collided and caused deterministic startup crashes. If NVIDIA crash reports come in, check the quirk crate first, not env vars.

## ALSA underrun (choppy audio) under load
rodio 0.19 + cpal use a small default ALSA buffer; CPU/compositor spikes miss the audio callback deadline. Mitigation: `PULSE_LATENCY_MSEC=60` set early in `run()` (Linux only, if unset) — helps under PipeWire/PulseAudio, no-op on pure ALSA. Real fix needs rodio 0.20+ (`OutputStreamBuilder`, explicit `BufferSize`) — deferred as too invasive.

## Read-only rusqlite can't own WAL `-shm` (fixed)
`library_read.rs` opened `canon.db` `SQLITE_OPEN_READ_ONLY`; can't create/recover `-wal`/`-shm` if the writer pool hasn't yet. Fixed: `SQLITE_OPEN_READ_WRITE | NO_MUTEX | URI` (still read-only in practice — no writes issued). `SQLITE_OPEN_CREATE` deliberately omitted so a bad path errors loudly. Not the "silent vanish" bug below — this one throws a query error, not a process death.

## Unbounded thread-per-request → SIGKILL (fixed)
Cover-art proxy spawned one OS thread per request, no cap. Rapid nav (sidebar switching) burst-spawned dozens, machine SIGKILLed the process (confirmed via `gdb --args` attach; exact external killer never IDed, doesn't matter). Fixed: permit acquired before spawn (backpressure, not queue buildup), now `tauri::async_runtime::spawn_blocking` on tokio's pool instead of raw `thread::spawn`, capped at 16 concurrent. Debug tell: `ps -eLf | grep canon | wc -l` climbing during repro, before assuming it's the WebKitGTK bug above.

## DNS resolver stalls → opaque "Load failed" after ~25s
Was host-machine systemd-resolved config (VPN nameservers pinned globally, unreachable off-VPN), not a Canon bug. All concurrent requests fail at the same instant because they block on the same DNS lookup, not each other; `curl` looks fine because it hits resolved's cache. Check before reading Canon's network code:
```
journalctl -u systemd-resolved --since "-1h" | grep -i "degraded\|timed out"
resolvectl status | head -20
sudo resolvectl flush-caches && time getent ahosts <server-host>
```
Canon-side hardening (`navigator.ts`/`sync.ts`) done regardless: `apiPost` 12s `AbortController` timeout (not `AbortSignal.timeout` — missing on old WebKitGTK), 3 retries w/ backoff, alt URL tried every attempt, named errors instead of `Load failed`. Loved/playlist sync stages non-fatal, reported via `skippedStages`; album-track pass gives up after 5 consecutive failures.

## Temp file keyed by shared id needs an in-flight guard in TS (fixed)
`audio_extract_waveform` writes to `temp_dir()/canon_wf_<track_id>.tmp` — two concurrent calls for the same track truncate/interleave each other, producing a corrupt cached waveform that looks like a persistent per-track bug. Reachable via normal preload + play-arrives-early race. Fix: `waveformInFlight: Set<trackId>` in `player.ts` — second caller skips invoke, attaches to the running extraction's events instead. **Generalizes:** any Rust command naming a temp/cache/lock file after a caller-supplied id is single-writer only if TS makes it so. Also: a command that `Err`s without emitting its completion event strands any one-shot `listen()` for that event — prefer one long-lived listener keyed by payload id.

## Async load handler overwrites input received mid-await (fixed)
`playTrack` awaited `.load()` then unconditionally set `isPlaying: true`; pause requests arriving during the await (space bar, media keys — skip the UI's `disabled={isLoading}` guard) got silently discarded. Fix: `pauseRequestedDuringLoad` flag, checked by the completion handler instead of asserting state. **Generalizes:** a track-id equality check ≠ intent check. Whenever a handler resumes post-await and writes state the user can also write, ask what happens if they wrote to it mid-flight. Same file: `resume()` also lacked a `currentTrack` guard, letting MPRIS start a ticker against silence.

## One cancellation counter shared by several commands cancels intent, not effect (fixed)
`AudioState.fade_gen` bumped by pause/resume/seek/volume; every fade thread exits on generation mismatch — correct for the ramp, wrong for the *action after* it (`audio_pause`'s terminal `sink.pause()` got skipped by unrelated bumps). Fix: separate `pause_pending: AtomicBool` carries intent, checked before the terminal action regardless of generation. Same pass: `audio_seek` no longer re-arms `play_start` when already paused (was making position climb against silent audio); ticker's natural-end fallback now requires `isPlaying`; a `seekGen` counter drops stale position polls that raced a seek. **Generalizes:** when several commands share one cancel token, check what each spawned task does *after* its loop — "work in progress" and "outcome the user wanted" are different things a single counter can't distinguish.

## Fast path bypassing the central action function skips every guard that function owns (fixed)
Gapless advance updates queue state directly on `track-advanced`, never calling `next()` — so `next()`'s sleep-timer check was dead on the default (gapless) path; "stop after this track" silently did nothing. Fix: guard duplicated at both ends — ticker won't hand off to gapless while sleep timer armed; `track-advanced` also pauses on arrival if armed late. **Generalizes:** when an optimization adds a second route to the same outcome, enumerate what the original route did *besides* the obvious thing.

## Optimistic suppression flag needs a cancellation event, not just a success event (fixed)
`gaplessActive` set the moment `audio_enqueue_next` is invoked (suppresses ticker's fallback advance) but only cleared on success (`track-advanced`) — the Rust thread has silent bail-outs (fetch/decode error, superseded `play_id`) that never told TS, so the flag stuck true and playback stalled dead. Fix: every bail-out path emits `gapless-cancelled`, cleared by a listener. Second bug same command: final `sink.append` was guarded by `play_id` alone, but a slow download could arrive after `track-ended` already fired on the now-empty sink — audible blip of wrong track. Fixed: check `sink.empty()` before appending. **Generalizes:** a fire-and-forget command owes the frontend an event on *every* terminal path, and a `play_id`-style guard only proves nothing newer started, never that the old thing is still wanted.

## A hand-off decided ahead of time must carry what it decided (fixed)
Gapless resolves `queueIndex+1` at 80% of the track and hands it to the engine; `track-advanced` then recomputed `queueIndex+1` again at the actual transition — any queue edit in that window (insert/reorder/remove/shuffle-reseed) resolved to a different track than what was actually playing. Fix: `gaplessEnqueued: {track, position}` records what was actually sent; `track-advanced` follows that track through edits instead of recomputing. Follow-up bug one level deeper: repeat-all re-shuffle anchored on the enqueued track, but that track had itself been position-0 of the *old* order, so every wrap re-opened on the same track forever (mirror bug on non-gapless path: `next()` always anchored `buildShuffleOrder(len, 0)`). Fix: new order built at enqueue time, travels as `gaplessEnqueued.wrapOrder`; `next()` passes `-1` (documented "no anchor"). **Generalizes:** whenever work is scheduled ahead of when it takes effect, the completion handler needs to be told what was scheduled, not re-derive it — and an anchor constant that's right at one call site isn't automatically right at another.

## A loading flag from `await invoke()` measures the IPC round trip, not the work (fixed)
`isLoading` cleared right after `invoke("audio_play")` resolved — but that command spawns its download/decode thread and returns immediately, so the flag vanished before any audio buffered. UI showed pause-icon/`0:00`/silence while claiming ready. Fix: separate `isBuffering` flag, cleared by the `audio-format` event (real start of audio) with ticker's first non-zero position as backstop; kept separate from `isLoading` so pause stays clickable during a slow buffer. **Generalizes:** if a command ends in `thread::spawn`/`spawn_blocking`, the promise resolves at hand-off not completion — only an event is honest. Same fix pass: `preloadWaveforms` (fired from `playTrack`'s completion) competed for bandwidth with the track still loading — gate background prefetch on audible playback, not on request.

## A stream that ends early looks identical to one that ended (fixed)
Download thread called `writer.finish()` (clean-EOF signal) on *every* exit path including read failures — decoder saw a well-formed short file, `track-ended` fired, next track played. A dying server mid-song looked exactly like a song ending normally. Fix: separate `fail()` (sets `failed`, reader returns `UnexpectedEof` after serving bytes that did arrive) vs `finish()`; download thread only calls `fail()` if `play_id` still matches (skip/stop isn't a failure). Same pass: `reqwest` HTTP error status wasn't checked (404/500 body streamed into the decoder as "unrecognised format" after wasting the retry budget); `Sink::try_new` error was `eprintln!` with no `emit`, leaving `isBuffering` stuck forever. **Generalizes:** "stream ended" and "stream stopped" are different signals a byte reader can't distinguish on its own — check every exit path maps to the right one.

## A proxy mapping a protocol's error channel onto success makes every downstream fallback dead code (fixed)
`upnp_soap` returned HTTP 500 (UPnP's only error channel — SOAP fault body) as `Ok`. `DlnaTarget.setNext`'s `catch`-based fallback for renderers lacking `SetNextAVTransportURI` could never run; `supportsSetNext` always recorded `true`. Fix: parse fault fields, return `Err` on 500. Consequence handled in the same pass: this makes transient faults loud, so `GetTransportInfo` failure now requires 3 consecutive before reporting error (was 1), plus a new `onError` callback. **Generalizes:** ask which outcomes are errors *in the wrapped protocol*, not which HTTP codes look alarming. Grep-worthy tells: a capability flag only ever assigned its optimistic value, or a fallback branch with no log line ever coming from it.

## A parallel-array invariant enforced by only one writer holds only until another writer runs (fixed)
`shuffleOrder` must satisfy `length === queue.length`; three writers (`toggleShuffle`, `playQueue`, `addToQueue`/`playNext`) handled the single-track case differently, so a shuffled 1-track queue + append produced a short/offset order — `?? position` fallback resolved two positions to one track (skip + duplicate) instead of crashing. Fix: `playQueue` writes `[0]` for single-track shuffle; `normalizeShuffleOrder` repairs any mismatched-length order before splice sites use it. **Generalizes:** when two arrays must stay index-aligned, the invariant belongs to the type, not the writers — an `?? fallback` on the lookup converts a crash into a silent wrong answer. Grep for a length guard (`if (n > 1)`) on one writer the others don't share.

## A resource acquired via await escapes the cleanup meant to free it (fixed)
`useWakeLock` stored its sentinel in a ref only after `navigator.wakeLock.request()` resolved; cleanup running during that await found `null` and freed nothing, then the resolved sentinel overwrote the ref with nothing left to release it. Fix: `cancelled` flag set by cleanup; resolved sentinel checks it and self-releases. Second bug same file: guard was `if (lockRef.current) return`, but the browser auto-releases on tab-hide, leaving a dead sentinel that blocked re-acquire — fixed to `!lockRef.current.released`. **Generalizes:** whenever an acquire is awaited and stored on resolve, teardown during the await has nothing to free — the acquiring path itself must free it. A handle another party can invalidate makes "is it non-null" the wrong liveness test.

## A normalize helper returning its input on the fast path hands callers the live state to mutate (fixed)
`normalizeShuffleOrder`'s `if (order.length === queueLength) return order` returned the caller's own live array; callers then `push`/`splice`d into it, mutating store state before `set()` ran and handing back the same reference — Zustand's reference-equality meant subscribers never re-rendered. Fix: `return [...order]` on every path. **Generalizes:** a "give me a safe copy" helper must copy on *every* path including the no-op one. Grep for a guard-clause return of the unmodified parameter whose callers then push/splice/sort into the result.

## A restore path writing `currentTrack` without loading the engine is unplayable (fixed)
Session restore set `queue`/`currentTrack` from a snapshot without calling `playTrack` — no `streamUrl`, no sink. `resume()` guarded only on `!currentTrack`/`error`, so pressing play set `isPlaying: true` against an empty sink; position stuck at 0 forever (stall watchdog needs position to have moved once). Fix: `resume()` treats null `streamUrl` like `error` — routes to `retryCurrent()`. Server-side restore had the opposite bug (called `playQueue()` then `pause()`, downloading a track nobody asked for) — replaced with a state-only `restoreQueue` action. **Generalizes:** `currentTrack != null` is the store's proxy for "engine has something loaded" — any restore path breaking that equivalence needs to either load the engine or make transport controls aware it didn't.

## A sync that only upserts diverges from its source, and the divergence feeds itself (fixed)
`syncLibrary` had no `DELETE` anywhere — server-side removals left orphan rows forever, and the incremental skip test (`existingTrackCount === songCount`) could never match again once one track was deleted, forcing full re-fetch + FTS/tag-vocab rebuild on every 5-min tick permanently. Fix: prune albums/tracks absent from the fetched list (and derived rows), excluding user-authored tables (`album_identity`, `album_user_genres`, scrobble history). Guards: prune refuses to run against an empty fetched list (misconfigured server ≠ delete-everything) or a partial one (`fetchAllAlbums` throws rather than returning short); a chunked `NOT IN` is refused outright (`executeIdChunks` is `IN`-only — chunking `NOT IN` deletes rows other chunks meant to keep).
Same pass, two more:
- **Playlist refresh was DELETE-then-INSERT**, silently dropping Canon-owned columns (`is_smart`, `rules_json`, `custom_cover_data`) the server payload doesn't know about. Fix: upsert naming only server-owned columns; prune only playlists absent from the fetch.
- **Loved-stage compare was asymmetric** (`WHERE track_id IN (SELECT ... server_id)` vs. write of every fetched id) — an orphan starred id (no local track) kept counts permanently unequal, full rewrite every 5 min forever. Fix: both sides scope by id prefix.
- **`playlist_tracks.position` doubles as remote Subsonic index** — deleting one row locally left a hole vs. server closing its own, so the second removal in a session hit the wrong remote track. Fix: compact positions post-delete via two negative-space passes (PK collision otherwise).
**Generalizes:** grep for `DELETE` against a mirrored table, not the write path (which reads complete regardless) — and ask what downstream logic depends on the *absence* of a row, since that's what silently breaks first.

## A skip heuristic freezes every column only the skipped path writes (fixed)
`tracks.play_count` was written only inside the (usually-skipped) track-fetch branch — froze at first-sync value forever for any listened-to library, silently, while `albums.play_count` (written every sync regardless) kept moving and hid the bug. Fix: `useScrobbleFlush` increments `tracks.play_count`/`albums.play_count` directly after each flush (after the queue DELETE, so a crash undercounts rather than double-counts; a later track-fetch overwrites with server truth anyway). **Generalizes:** whenever a sync gains a skip fast-path, list every column the skipped path is the sole writer of — those freeze for as long as the skip condition holds.

## A drain loop that breaks on any error blocks on its first permanent failure (fixed)
`useScrobbleFlush` `break`'d on any thrown error — right for "server unreachable," wrong for Subsonic error 70 (track deleted server-side, fails identically forever), which then blocked every row behind it, unboundedly inflating the "pending" play count. Fix: `SubsonicError` carries the error code; code 70 drops the row and continues, everything else still breaks (auth codes 40/41/50 deliberately kept in the "breaks" set — re-entering a password makes those recoverable, dropping them would delete the offline backlog). Second bug same file: no in-flight guard — a flush pass slower than the 60s interval could overlap the next tick and double-send a scrobble. Fix: `flushing` flag (same shape as `waveformInFlight` above). **Generalizes:** ask (1) can one item fail permanently and does the error channel let the loop tell, (2) can one pass outlast its interval and what stops re-reading undeleted work.

## A repair effect whose repair invalidates its own trigger data can loop forever (fixed)
`AlbumDetail`'s bitrate-backfill effect ended in `bumpRefresh()`, which its own `tracks` dep re-fetched — if the condition was genuinely unrepairable (server really reports no bitrate), the effect re-ran and re-synced over the network at full speed, indefinitely, silently. Fix: `useRef` marking the album id already attempted, stamped *before* invoking the repair. **Generalizes:** any effect whose write reaches the data its own condition reads needs an attempt-marker (claimed by the attempt, not the success) or a genuinely unrepairable condition retries forever. Grep for an effect calling `bumpRefresh()`/`invalidateQueries` while depending on the value that call refetches.
Related, same pass: **selection stored as row indices silently repoints on reorder/refresh** (`TrackTableView` held `Set<number>`) — store selection by stable id, resolve to index only at click time.

## A prefetch that duplicates a query instead of sharing it warms a key nobody reads (fixed)
`useNowPlayingPrefetch` held its own copy of `NowPlayingView`'s query fns/keys — derived the cache key from raw `currentTrack.artist` while the tab derived it from the feat.-stripped artist, so "X feat. Y" tracks always missed the prefetch (2x wasted Last.fm calls) *and* separately hit a broken SQL string (`` ESCAPE '\' `` inside a JS template literal is `ESCAPE ''`, which SQLite rejects outright) — each bug hid the other. Fix: shared `now-playing-queries.ts` module for query fns/keys/staleTime, real `ESCAPE '\\'`. **Generalizes:** a prefetch is only a prefetch if key, `queryFn`, and `staleTime` (consumer's ≥ prefetch's — it's an observer property, not cache-entry property) are byte-identical to the consumer's, not equivalent-looking copies. Grep repo-wide: **`ESCAPE '\'` inside any template literal or single-quoted TS string is always `ESCAPE ''` and always throws.**

## A `LIMIT` without `ORDER BY` silently redefines what the query returns (fixed)
Three FTS search queries capped `LIMIT 200` with no `ORDER BY` — FTS5 returns rowid order absent one, so the cap kept the 200 *oldest-synced* rows, and the JS relevance-ranking after it looked like it was ranking real candidates while ranking an arbitrary sample (broad queries could drop the exact-title match entirely, invisibly). Fix: shared `MATERIALIZED` CTE ranks by weighted `bm25` before the cap (`MATERIALIZED` is load-bearing — a plain CTE gets flattened and SQLite rejects `bm25` in that context; bm25 also can't appear inside an aggregate — rank in the CTE, aggregate its column). **Generalizes:** any `LIMIT` without `ORDER BY` is a silent sampling decision by whatever the engine visited first — ask "was the cut thing chosen or just late," not "is the output sorted" (a later JS sort disguises this).
Same pass: search also had no `server_id` filter, with call sites reconstructing `server_id: server.id` from the *currently selected* server rather than the row — see the ownership-column entry below, found here a fourth time. Also: `useDeferredValue` defers rendering, not fetching — using it to gate a `queryKey` still fires once per keystroke; not a debounce substitute.

## An identifier borrowed from an external service is compared exactly against a local one (fixed)
`useSimilarInLibrary` compared Last.fm artist names against local ones via exact string match — capitalization/alias differences ("Tyler, The Creator" vs "...the...") misfiled owned artists as unowned, and the same borrowed string then addressed an equally-exact lookup in `ArtistDetailRoute`, landing on a synthesized empty fallback row that looked like a real (wrong) page. Fix: both sides key on `LOWER(TRIM(...))`, ownership query unions `artist_aliases`, route selects the library's own `a.name` for downstream queries. **Generalizes:** any string from Last.fm/MusicBrainz/server response used as a join key needs normalization on both sides — and a bad match that *also* addresses a second lookup compounds; check every hop, not just the first comparison.
Related, same route: `data ?? fallback` on a `useQuery` result renders the fallback during loading too (`data` is `undefined` both while pending and when genuinely null) — always check `isPending` first.

## A mirror not scoped by owner depends entirely on its delete path (fixed)
`albums`/`tracks`/`artists`/`playlists` carry `server_id` but no read query filtered on it — removing a server left its whole library mixed into the grid (playable, 404s on stream). Fix: `purgeServerData` called before the `servers` row delete. **Generalizes:** an unfiltered ownership column is a comment, not an invariant — either reads enforce it or a delete path must; grep the read path for the column, not the schema.
**Sharper form, found later on the home screen and in search:** the dangerous move isn't the unscoped read, it's *reconstructing* the owner afterward — several call sites built `AlbumRow`/`SearchAlbum` with `server_id: server.id` (currently selected server) instead of selecting the owner column from the row. This degrades silently: internally consistent object, wrong host, passes every type check. **Grep for any object literal assigning `server_id:` from a variable that isn't the source row.**

## A geometry constant in TS restating a CSS value drifts silently (fixed)
`AlbumCarousel` scrolled by a hardcoded `168 + 14` px/card; actual CSS was `160px + 12px gap` — small per-click overscroll accumulates into visible misalignment after a few clicks, reading as a rendering bug rather than a stale constant. Fix: measure from the DOM at use time (`offsetWidth` + computed `columnGap`). **Generalizes:** any TS number that only makes sense because of a CSS value is a copy with no link back. Grep for bare-pixel arithmetic in a component whose CSS defines the same dimension — a literal written as a sum (`168 + 14`) is the tell someone hand-reproduced a box model. Known open instance: `AlbumGrid.tsx:316` scrubber jump is off by `PADDING` for the same reason.

## Secret written before its owning row outlives the row (fixed)
Server setup wrote the keychain credential under a freshly minted id, then inserted the `servers` row — a failed insert orphaned the keychain entry (unfindable, and every retry mints a new id, stranding another copy). Removal had the mirror bug: row deleted first, keychain delete wrapped in a swallowed `catch`, so a locked keychain left the secret behind with nothing referencing it. Fix: insert paths roll back the keychain write on failure; removal deletes the keychain entry first and aborts (surfacing the error) if that fails. **Generalizes:** when a secret and its owning row live in different stores, write order decides which failure is recoverable — create the reference last but roll back on failure; delete the reference last so a failed secret-delete stays retryable.
Related, same pass: `keychain.get` *rejects* on a missing entry (doesn't resolve `""`), so a `if (!credJson) throw ...` null-check at the call site was dead code and the user saw the raw keyring error instead of the friendly message. Grep for any `invoke()` wrapper whose caller null-checks the resolved value. Also: that query inherited global `retry: 3` — a permanently-missing-secret failure should be `retry: false`.

## A frontend feature can be dead on the default path (fixed)
See "fast path bypassing central action" and "gapless bypassing sleep timer" above — same lesson, worth its own reminder: when a code path exists that skips the normal function, audit it against every side effect that function had, not just the one that motivated the optimization.
