# Known Issues & Platform Gotchas

Bug classes that already shipped once. Headings are the lesson. Full forensics in git history.

## Platform (Linux / WebKitGTK / audio)

**Left-click popup self-closes.** Outside-click listener catches the tail of the opening click (WebKitGTK only; right-click fine). Fixed in `ContextMenu.tsx`: listener deferred `setTimeout(...,0)`, uses `mousedown` capture + containment, not `click`. New left-click popover "does nothing" → same class, check render fires but `querySelector` finds nothing.

**Freeze/thaw compositor crash.** Focus loss/regain can kill the WebProcess (`gdk_window_thaw_toplevel_updates`); `wry` doesn't survive it. Upstream bug. Mitigations, all active, don't strip without replacing: `web-process-terminated` → `.reload()` in `lib.rs .setup()`; `useAppActivityTracking` stamps `data-app-blurred`, CSS pauses animations; `webkit2gtk-nvidia-quirk` crate (skip via `CANON_WEBKIT_GPU_ACCEL=1`); `"visible": false` + `window.show()` on `on_page_load` with 5s fallback thread. **Never** call `set_hardware_acceleration_policy` without auditing what else touches compositing - `OnDemand` + `WEBKIT_DISABLE_COMPOSITING_MODE` collided into deterministic startup crashes.

**ALSA underrun under load.** rodio 0.19 + cpal small default buffer misses callback deadlines on CPU spikes. Mitigated by `PULSE_LATENCY_MSEC=60` set early in `run()` (Linux, if unset). Real fix needs rodio 0.20+ `OutputStreamBuilder`; deferred.

**Read-only rusqlite can't own WAL `-shm`** (fixed). `library_read.rs` now opens `READ_WRITE | NO_MUTEX | URI` (still issues no writes); `CREATE` deliberately omitted so a bad path errors loudly.

**Unbounded thread-per-request → SIGKILL** (fixed). Cover proxy spawned an OS thread per request; rapid nav burst-spawned dozens. Fixed: permit acquired *before* spawn, `spawn_blocking` on tokio pool, cap 16. Debug tell: `ps -eLf | grep canon | wc -l` climbing.

**Opaque "Load failed" after ~25s** was host systemd-resolved (VPN nameservers pinned globally), not Canon. All requests fail simultaneously because they share one DNS lookup; `curl` hits resolved's cache and looks fine. Check `journalctl -u systemd-resolved | grep -i "degraded\|timed out"`, `resolvectl status`, `resolvectl flush-caches && time getent ahosts <host>` before reading network code. Hardening done anyway: 12s `AbortController` timeout (not `AbortSignal.timeout`, missing on old WebKitGTK), 3 retries w/ backoff, alt URL every attempt, named errors; loved/playlist stages non-fatal via `skippedStages`; album-track pass gives up after 5 consecutive failures.

## Async / lifecycle classes

**A command naming a temp file after a caller-supplied id is single-writer only if TS makes it so** (fixed). Two `audio_extract_waveform` calls for one track truncated each other's `canon_wf_<id>.tmp`. Fix: `waveformInFlight: Set<trackId>` in `player.ts`. Also: a command that `Err`s without emitting its completion event strands one-shot `listen()`s - prefer one long-lived listener keyed by payload id.

**A handler resuming post-await must check intent, not assert state** (fixed). `playTrack` set `isPlaying: true` after `.load()`, discarding pauses that arrived mid-await (space/media keys bypass `disabled={isLoading}`). Fix: `pauseRequestedDuringLoad` flag. Track-id equality ≠ intent. Same file: `resume()` lacked a `currentTrack` guard, letting MPRIS tick against silence.

**One cancel token shared by several commands cancels intent, not effect** (fixed). `fade_gen` bumps by pause/resume/seek/volume skipped `audio_pause`'s terminal `sink.pause()`. Fix: separate `pause_pending: AtomicBool` checked before the terminal action regardless of generation. Ask what each spawned task does *after* its loop. Same pass: `audio_seek` no longer re-arms `play_start` while paused; ticker's natural-end fallback requires `isPlaying`; `seekGen` drops stale position polls.

**A fast path around the central action skips every guard that action owns** (fixed). Gapless advance mutated queue state on `track-advanced` without calling `next()`, so the sleep-timer check was dead on the default path. Fix: guard at both ends. When an optimization adds a second route, enumerate what the original did *besides* the obvious thing.

**A fire-and-forget command owes an event on every terminal path** (fixed). `gaplessActive` set at invoke, cleared only on success; Rust's silent bail-outs stalled playback dead. Fix: every bail-out emits `gapless-cancelled`. A `play_id` guard proves nothing newer started, never that the old thing is still wanted - final `sink.append` also checks `sink.empty()` now (slow download arriving after `track-ended` played a blip of the wrong track).

**Work scheduled ahead of time must carry what it decided** (fixed). Gapless resolves `queueIndex+1` at 80%; `track-advanced` recomputed it, so any queue edit in that window played a different track. Fix: `gaplessEnqueued: {track, position}`, followed through edits. Deeper: repeat-all re-shuffle anchored on the enqueued track, itself position-0 of the *old* order → every wrap reopened the same track (mirror bug: `next()` always anchored `buildShuffleOrder(len, 0)`). Fix: order built at enqueue time, travels as `gaplessEnqueued.wrapOrder`; `next()` passes `-1` = no anchor. An anchor constant right at one call site isn't right at another.

**A loading flag from `await invoke()` measures the IPC round trip, not the work** (fixed). `audio_play` returns at thread hand-off, so `isLoading` cleared before any audio buffered. Fix: separate `isBuffering`, cleared by the `audio-format` event with first non-zero ticker position as backstop; kept distinct so pause stays clickable. If a command ends in `thread::spawn`/`spawn_blocking`, only an event is honest. Same pass: `preloadWaveforms` now gates on audible playback, not on request.

**"Stream ended" and "stream stopped" are different signals** (fixed). Download thread called `writer.finish()` on every exit incl. read failures, so a dying server looked like a finished song. Fix: `fail()` (reader returns `UnexpectedEof`) vs `finish()`; `fail()` only if `play_id` still matches (skip isn't failure). Same pass: `reqwest` HTTP status now checked (404 bodies were decoded as "unrecognised format"); `Sink::try_new` error now emits instead of `eprintln!` (was stranding `isBuffering`).

**A resource acquired via await escapes the cleanup meant to free it** (fixed). `useWakeLock` stored its sentinel only on resolve; cleanup during the await freed nothing. Fix: `cancelled` flag set by cleanup, resolved sentinel self-releases. Also `if (lockRef.current) return` was wrong - browser auto-releases on tab-hide, so test `!lockRef.current.released`. A handle another party can invalidate makes non-null the wrong liveness test.

**A guard keyed on one concrete error type stands in for the broad condition it was meant to test** (fixed). `apiPost` gives a non-idempotent write (`scrobble`, `createPlaylist`, `updatePlaylist`, `deletePlaylist`) exactly one attempt by setting `maxAttempts = 1`, which disarms the *retry* loop but not the *url* loop: the alt route was still tried inside that single attempt, and the only escape was `if (!retriable && isTimeout(err)) break`. `isTimeout` is `err instanceof DOMException && err.name === "AbortError"`, so the guard covered only Canon's own 12s abort. The dominant Linux failure - the systemd-resolved stall recorded above - rejects with an opaque `TypeError("Load failed")`, which fell straight through and re-sent the same write to the alt host. So duplicate-suppression existed exactly for the failure Canon generates itself and was absent for the one the network generates: a play scrobbled twice, or a track added twice by `updatePlaylist`, which is the endpoint behind every playlist add/remove/replace. Fix: `if (!retriable) break` - both urls are routes to the *same* Navidrome, and `fetch` cannot distinguish "never opened a connection" from "applied and lost the response", so any rejection has to be read as "may already have been applied". An idempotent endpoint still tries both routes. **Generalizes:** the question a guard is asked ("was this write applied?") and the question it actually answers ("did this specific error type occur?") drift apart silently, because the narrow test is *correct for every case its author reproduced* - a timeout is easy to trigger by hand, a resolver stall is not. When a branch decides whether a side effect may repeat, it must default to the unsafe assumption on every error it does not recognise, never the safe one. The comment is the tell: `apiPost`'s said the alt route was used "only when the first one never reached the server at all", a guarantee the code never delivered. Grep tell - a control-flow branch keyed on one error class or name:
```
grep -rn "instanceof DOMException\|AbortError\|instanceof TypeError\|err\.name ===" src --include='*.ts*' | grep -v '\.test\.'
```
Every hit must either be building a *message* (`describeError` is the legitimate one) or be a branch whose non-matching errors provably belong on the other side. A hit deciding whether to repeat a write is an instance of this bug.

## Test / harness classes

**Advancing fake time across a span costs one iteration per live interval tick, and the price is invisible in the assertion** (fixed). `player.test.ts`'s sleep-timer block set each case up with `play()`, which arms the store's 200ms position ticker, and then advanced 30 to 60 minutes of fake time to reach the `setTimeout` the sleep timer had armed. `advanceTimersByTimeAsync` runs every timer due in that span, so the ticker fired 9,000 to 18,000 times per case, each firing a promise chain through the mocked `audio_get_pos`. Measured: 30 minutes cost 2837ms, an hour cost 4729ms, against vitest's 5000ms default - so the block failed roughly one run in three, as `Error: Test timed out in 5000ms.` on whichever cases lost the race, and every extra bit of machine load moved more of them over the line. It read as a contention or ordering bug (and was filed as one, blamed on `advanceTimersByTimeAsync` outrunning a pending `audio_pause` resolution) because the failing case varied per run and the failure rate rose under load - but the cost is deterministic and proportional to the *advanced span*, not to anything racing. Fix: the sleep timer never reads the ticker, so the four slow cases set the playing state directly (`currentTrack`/`streamUrl`/`isPlaying`) instead of calling `play()`; the spans and every assertion are unchanged and the cases now run in 1ms. Not fixed by raising the timeout, which would have kept an hour of wall-clock-proportional work in the suite and just moved the cliff.

**Generalizes:** fake timers make a long span look free, and it is free only if nothing short-period is armed. Any test that both starts a component or store which polls, and then advances minutes or hours to reach a distant timer, is paying `span / period` iterations, and the assertion that follows says nothing about it. The tell is a test whose duration tracks the number it advances by rather than the work it checks, and the symptom is a timeout that lands on a different case each run - which is exactly what a race looks like, so the diagnosis goes wrong before anyone times it. Time the cases before theorising: `--testTimeout=60000 --reporter=verbose` prints per-case durations, and a duration proportional to the advanced span settles it in one run. Either stop the poller for the span, or set the state the distant timer needs directly and leave the poller out of the case. Grep tell - a large fake-time advance, which is only safe with nothing polling underneath it:
```
grep -rn "advanceTimersByTime" src --include='*.ts*' | grep -E "60 \* 1000|3600|\* 60 \*"
```
Every hit must be in a test that has not armed an interval, or must say why the iteration count is affordable.

## Data / state classes

**A parallel-array invariant enforced by one writer holds only until another runs** (fixed). `shuffleOrder.length === queue.length` broke on shuffled 1-track queue + append; the `?? position` fallback turned a crash into a silent skip+duplicate. **A restore path writing `currentTrack` without loading the engine is unplayable** (fixed). No `streamUrl`, no sink, position stuck at 0 forever. **A sync that only upserts diverges from its source, and the divergence feeds itself** (fixed). `syncLibrary` had no `DELETE`: orphan rows forever, and `existingTrackCount === songCount` could never match again, forcing a full re-fetch + FTS rebuild every 5 min permanently. Grep `DELETE` against mirrored tables, and ask what depends on a row's *absence*.

**A skip fast-path freezes every column only the skipped path writes** (fixed). `tracks.play_count` lived in the usually-skipped track-fetch branch and froze at first-sync value, while `albums.play_count` kept moving and hid it. Fix: `useScrobbleFlush` increments both after each flush (after the queue DELETE, so a crash undercounts rather than double-counts). **A drain loop that breaks on any error blocks on its first permanent failure** (fixed). `useScrobbleFlush` broke on Subsonic error 70 (track deleted server-side, fails forever), blocking every row behind it. **A statement sequence whose intermediate states are invalid is a transaction, whether or not anyone wrote one** (fixed in the migration runner; open elsewhere). `runMigrations` split each block's `sql` on `";"`, ran the statements one at a time with no `BEGIN`/`COMMIT`, and recorded `schema_migrations` only after the last one succeeded. So a block that died partway (crash, disk full, killed process) committed its earlier statements, did not advance the version, and the next launch replayed the block from statement 1 against a database it had already half-changed. Two blocks made that unrecoverable rather than noisy: **v25 and v35 rebuild `track_tags`** as `CREATE track_tags_new` / `INSERT ... SELECT` / `DROP track_tags` / `RENAME`, so dying between the DROP and the RENAME leaves every tag Canon ever pulled in a table the app cannot see, and the replay then dies on `CREATE TABLE track_tags_new` (already exists) on every launch forever; and **v27's `INSERT INTO tag_vocab_cache`** had no `OR IGNORE` against a `(norm_value, kind)` PK, so a replay after that statement had run failed with a UNIQUE violation - but only on a non-empty library, which is why it was never seen in development. Fix: each block's statements *and its version row* run inside one `BEGIN`/`COMMIT`, with `ROLLBACK` on any failure and the original error rethrown (a failing ROLLBACK must not replace the error that says what went wrong); v27's seed gained `OR IGNORE` so a replay survives even if a future block escapes the transaction.

**A stored version number compared in one direction only answers "what still needs doing", never "is this file too new for me"** (fixed). `runMigrations` read `MAX(version)` off `schema_migrations` and ran every block above it. A version *higher* than the newest declared block simply matched no block, so the loop body never ran and the runner returned success - an older Canon then issued its own queries against a schema a newer build wrote. Reachable by installing a release, opening it, and rolling back, or by syncing `canon.db` between machines on different versions. The failure is not at startup where it could be named: extra columns are harmless, so what the user sees is a scattering of unrelated-looking errors deep in sync or tag normalization, or a `CHECK` a later migration tightened rejecting a write. Fix: `LATEST_SCHEMA_VERSION` (max of the declared blocks) and a `SchemaTooNewError` thrown before the loop when `current > LATEST_SCHEMA_VERSION`; `App` renders it through `src/app/DatabaseErrorScreen.tsx` with its own copy and **no "Try again" button**, because there is no downgrade path and a retry cannot change the answer - and `useServers` drops its retries for that error class so the message is not delayed by three backoffs of a permanently failing read. Note the guard is `>`, not `>=`: an up-to-date database is not a too-new one, and that is pinned by its own test. **Generalizes:** a high-water mark is a lower bound, so code that only ever asks "is the stored number below mine" is silently assuming it can never be above; the assumption is invisible because the over-version case produces *success*, not an error, and the damage lands somewhere else entirely. Any persisted format/schema/protocol version wants a *supported ceiling* alongside the target, checked at open, failing with a message that names both numbers. Grep tell - a stored version compared with `>`/`<` in one direction, or a migration/high-water loop with no ceiling:
```
grep -rn "schema_migrations\|user_version\|SCHEMA_VERSION" src src-tauri/src | grep -v '\.test\.'
```
The only writer today is `src/db/migrations.ts`; a second store of versioned state (a cache format, an exported library file, a sidecar) reintroduces the class unless it carries its own ceiling.

**A transaction written in TypeScript is a transaction only where nothing else can query, so the second instance of the class could not reuse the first one's fix** (fixed). The migration-runner entry above ends by naming its own escape hatch: "a single Rust-side transaction (`rusqlite`, `db_path()` already exists in `library_read.rs`), not a bigger TS one". `usePlaylistTracks.removeTrack` was the open instance recorded beside it, and it is on the far side of exactly that line. Its four statements - `DELETE FROM playlist_tracks`, then `position = -(position - 1)`, then `position = -position`, then the `playlists.track_count` decrement - move every surviving row through **negative** positions, deliberately, because `PRIMARY KEY (playlist_id, position)` is enforced per row and a single in-place decrement collides with the row still holding the target position whenever SQLite scans descending. Dying between the two passes (crash, kill, disk full) leaves rows at negative positions, and nothing repairs that: the load query's `ORDER BY pt.position ASC` renders them ahead of position 0, the row numbering shows negatives, and the next removal hands Navidrome a `songIndexToRemove` computed from a negative position, deleting a track nobody asked for. `track_count` is left un-decremented on top.

The reason the fix is not `BEGIN`/`COMMIT` in the hook: `tauri-plugin-sql` 2.4.0 builds its pool with `Pool::connect(conn_url)` (`wrapper.rs:91`), which is sqlx's default of **10 connections with no affinity**, and it exposes no handle to pin one. The migration runner gets away with a TS transaction for a reason that does not generalize - its awaits are strictly sequential *and* `getDb()` gates every other caller behind the same promise, so the pool never has cause to open a second connection while it runs. A playlist removal is a user gesture that lands whenever the user clicks, with the 5-minute library sync and every mounted read hook querying the same pool; a `BEGIN` there can be issued on one connection and its statements on another, which silently makes the transaction a no-op *and* deadlocks the second connection against the write lock it is holding. Fix: `src-tauri/src/library_write.rs`, a `playlist_remove_track` command running all four statements in one `rusqlite` transaction on its own connection, with the hook reduced to "tell the server, then invoke it". Table-state coverage moved to Rust with it, including a trigger that aborts the second compaction pass to stand in for the process dying between them - the one assertion the TS suite could never make, since `FakeDatabase` is a single connection and would have made a TS `BEGIN` look correct.

**Generalizes:** "wrap it in a transaction" is not a portable fix - it is a claim about the *connection*, and a pooled client that hands out a connection per statement cannot make that claim no matter how the SQL is written. Before writing `BEGIN` anywhere, ask what guarantees the next statement reaches the same connection, and treat "nothing else queries right now" as a property of the *call site*, not of the code: a startup path can promise it, anything reachable from a user gesture cannot. The tell is that the broken version passes every test, because a test harness is single-connection and single-threaded by construction. Grep tell - who writes a transaction from TS, and against which call sites:
```
grep -rn '"BEGIN"\|BEGIN TRANSACTION' src --include='*.ts*' | grep -v '\.test\.'
```
The only legitimate hit is `src/db/migrations.ts`, and only because of the gating described above; any new hit reachable from a handler belongs in `library_write.rs` instead.

**The subtle part is not the transaction, it is that the transaction is only real if the statements reach the same connection.** `tauri-plugin-sql` runs every `execute()` through `pool.execute(...)` on an sqlx pool (`Pool::connect`, default max 10 connections) with no connection affinity, so `BEGIN` and the statements after it are *not* guaranteed to share a connection in general. It holds here for one specific reason: the runner's awaits are strictly sequential and `getDb()` (`src/db/index.ts`) gates every other caller behind the same promise, so the pool never has cause to open a second connection while a migration is in flight. Anything that starts issuing queries concurrently with the runner silently turns the transaction into a no-op *and* deadlocks the second connection against the write lock. That constraint is written into the comment at the `BEGIN`; the escape hatch if it is ever broken is a single Rust-side transaction (`rusqlite`, `db_path()` already exists in `library_read.rs`), not a bigger TS one.

**Generalizes:** any run of statements where an intermediate state is not a state the program can start from is a transaction that somebody forgot to open, and it reads as fine because the only way to see it is to kill the process at the right moment - no test, no manual run, and no code review of the happy path will show it. Ask, per statement, "if the process dies right here, does the *first* statement still work next launch?" - not "do these statements do the right thing in order". A retry loop, a resume path, or a version high-water mark all make it worse rather than better, because they guarantee the half-state is replayed rather than merely abandoned. **Decoding a value the framework already decoded is a no-op on almost every input, and a crash on the rest** (fixed, 3 sites).
