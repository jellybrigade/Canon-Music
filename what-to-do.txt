--- Genre Overhaul ---

GOAL: Albums always have normalized, canon-tree-resolved genres sourced from MB + Last.fm,
with unresolvable tags flagged for manual matching.

## Trigger points
- Album detail opens → background-fetch MB + Last.fm genres for that album
- Settings "Sync all MB" → bulk background fetch MB genres for all albums in library
- Settings "Sync all Last.fm" → bulk background fetch Last.fm tags for all albums in library
  (these already exist as buttons; they need genre-resolution wired in)

## MB auto-identify
- On album open, if MB search returns top candidate with confidence >80% (title + artist fuzzy
  match), auto-confirm identity silently (same logic already noted in auto-verify note below)
- Genres come from the confirmed MB Release Group + Release combined (already implemented in
  useAlbumIdentity / combineGenres — just need to wire it to the auto-identify trigger)

## Genre normalization pipeline (for BOTH MB and Last.fm genres)
1. Receive raw genre strings (e.g. "j-euro", "Hip-Hop", "post-punk")
2. Fuzzy-match each against canon-tree.json nodes (canonical_key, Levenshtein ≤2)
3. If matched → resolve to canonical node + walk full ancestor chain up the DAG
   Example: "j-euro" → J-Euro + Wa Euro + J-Pop (all ancestors included, not just leaf)
4. Store resolved set (leaf + all ancestors) in album_identity or new genre_resolved table
5. If not matched → add to genre_mappings queue as "needs review" — surface in tag mapping UI
   so user can manually map it to the right canon node (or mark as unmappable)

## Display
- Album detail shows resolved genres (the normalized + expanded set)
- Genre chips use canonical names (J-Euro, not j-euro)
- Ancestor genres visible — so clicking "J-Pop" finds all J-Euro albums too (already how
  filter should work if genres stored correctly)

## Unmatched genre flow
- Genres that couldn't be resolved appear in a "tag mapping" view (the tagging menu)
- User picks the correct canon-tree node (or creates a new mapping)
- Approval writes to genre_mappings table → re-run normalization for affected albums

## What needs building
- Auto-identify trigger on album open (background, silent if confident)
- Genre normalization function: raw string → canonical node + ancestors via canon-tree DAG walk
- Storage: where resolved genres live (extend album_identity.combined_genres_json, or new table)
- Wire "Sync all MB" + "Sync all Last.fm" buttons to run normalization pipeline after fetch
- Tag mapping UI to handle unmatched genres (may reuse/extend existing genre_unifier flow)
- AlbumDetail renders resolved genres from the new source instead of raw file tags

--- Album Identification / Right-Click Lookup Popup ---
- Right-click album → context menu → "Album Info / Identify..."
- Opens modal showing auto-detected match status for MusicBrainz + Last.fm:
    MusicBrainz: found ✓ / not found ✗ / ambiguous ? + key facts (title, artist, year, label)
    Last.fm: found ✓ / not found ✗ + key facts (play count, tags)
- Two MB ID levels matter:
    Release Group MBID = the abstract album (e.g. "Kind of Blue" regardless of edition) — primary anchor
    Release MBID = specific pressing (catalog #, barcode, country) — optional, for exact tag writes
- Last.fm has no stable album ID — it matches by artist name + album name strings.
  "Correction" for Last.fm = fix the name strings used to query it, not paste an ID.
  (Last.fm also returns MBIDs in responses — so a confirmed MB Release Group MBID serves as Last.fm anchor too)
- Editable fields in popup: MB Release Group MBID, MB Release MBID (optional), MB Artist MBID
  + corrected artist name / album name strings for Last.fm fallback
- "Re-fetch with these IDs" action re-runs both lookups with the corrected values
- Confirmed identity persists to new SQLite table:
    album_identity(album_id, mb_release_group_id, mb_release_id, mb_artist_id, lastfm_match_confirmed)
  Overrides auto-lookup. Feeds tag-write flow via pending_edits.
- Same popup (or variant) should work on Artist page for artist MBID correction

--- Code Quality ---
- rawGenre IN filter fragile: useAlbums.ts does exact-match WHERE t.genre IN (?) against the
  full stored genre string. Currently safe because unmapped chips pass the full raw_value (e.g.
  "Rock, Pop") which matches exactly. But if any layer ever tokenises the chip name before passing
  rawGenre, the filter silently returns 0 results. Fix: either store genres as individual tokens
  in SQLite, or use a LIKE/INSTR query instead of IN for the raw genre path.
